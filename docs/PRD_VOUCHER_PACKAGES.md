# PRD：商品券／多堂課方案

## Overview

### Problem Statement

目前 Bookr 的課程只有單次定價，預約也只保存單次課程的價格快照。店家若要提供「一次購買多堂、平均單價較低」的方案，只能在系統外記錄購買、剩餘堂數與扣堂，容易發生漏扣、重複扣除、到期爭議，也無法在預約時自動優先使用客戶已購買的商品券。

現在預約、客戶、課程與 LINE 身分串接已可正常運作，適合加入一個與既有預約生命週期整合的商品券模組，讓銷售、預約保留、完課扣堂與餘額查詢都有可追溯紀錄。

### Solution Summary

建立「商品券方案」及「客戶持有商品券」兩層資料：

1. 店家建立商品券方案，設定售價、有效期，以及可兌換的一個或多個現有課程與各自堂數。
2. 員工將商品券售予既有客戶，系統保存當下的售價、內容與效期快照。
3. 客戶預約符合條件的課程時，系統預設使用最接近到期的商品券，先保留一堂；完課時正式扣堂，取消時歸還。
4. 後台可查看每位客戶的剩餘、已保留、已使用與已到期堂數，以及完整異動紀錄。

本功能為確定性商業邏輯，不包含 AI 產生內容。

### Target Users

- 店家管理員：建立與管理商品券方案、銷售商品券、查詢與調整堂數。
- 店家一般成員：替客戶預約、查看可用商品券及本次使用狀態；是否可銷售或調整由角色權限控制。
- 客戶：購買多堂方案，預約時自動使用適用商品券，並在預約結果與 LINE 通知中得知使用及餘額。

## Goals & Success Metrics

### Goals

1. 讓店家能在 Bookr 內建立並販售多堂優惠方案與跨課程組合。
2. 讓符合資格的預約自動優先使用商品券，且不會超扣或出現負數餘額。
3. 讓每一堂的保留、扣除、釋放與人工調整都有可稽核紀錄。
4. 保持既有單次課程定價、預約與 LINE 通知流程可正常運作。

|--------|-----------------|--------|----------|
| 建立一個商品券方案所需時間 | 尚無此功能 | 一般方案在 2 分鐘內完成 | Staging 驗收 |
| 登記一筆商品券銷售所需時間 | 系統外處理 | 60 秒內完成 | Staging 驗收 |

| 既有非商品券預約回歸通過率 | 現行功能正常 | 100% 關鍵流程通過 | 每次部署前 |

### Non-Goals

- 本期不串接線上刷卡、第三方支付、發票或自動對帳。
- 本期不建立折扣碼、滿額折扣、點數或現金儲值功能。
- 本期不支援跨店共用、轉讓、贈送或家庭共享商品券。
- 本期不支援商品券的部分退款、自動退款或會計遞延收入報表。

## Scope

### In Scope

- 商品券方案的建立、編輯、上架、下架與軟刪除。
- 單一課程多堂方案，以及由多個既有課程及各自堂數構成的組合方案。
- 後台將方案售予既有客戶；可記錄實收金額、付款方式及備註，但不處理金流。
- 客戶持有商品券的有效期、狀態與剩餘堂數管理。
- 建立預約時自動選用商品券、保留堂數、完課扣堂、取消釋放。
- 改期、改課程、未到場及商品券到期等生命週期處理。
- 客戶詳情、預約詳情與商品券管理頁的查詢及異動紀錄。
- LINE LIFF 客戶中心的「我的預約」及「我的商品券」唯讀查詢。
- 店家隔離、角色權限、稽核紀錄、併發扣堂保護。
- 商品券使用資訊納入既有預約 LINE 通知範本可用資料。

### Out of Scope

- 客戶自助線上購買、付款、退款與電子發票。
- 不對既有歷史預約自動回溯套用商品券。
- 商品券轉讓、多人共用、跨店兌換與拆分合併。
- 不以商品券取代現有課程；實際排程仍必須對應一筆現有課程。
- 複雜促銷規則，例如限時折扣、買贈、會員等級價與動態定價。

### Future Considerations

- 客戶端商品券錢包與購買入口。
- 線上支付、退款、發票與付款狀態同步。
- 可跨多個適用課程共用的「通用點數池」。
- 家庭共享、轉贈、跨分店使用。
- 到期提醒、餘額不足提醒與促銷自動化。
- 商品券銷售、使用率、未履約餘額與收入認列報表。

## Solution Design

### Product Model

產品上區分三個概念：

- **商品券方案**：店家可重複銷售的範本，例如「深層按摩 10 堂優惠券」或「肩頸 3 堂＋全身 2 堂組合」。
- **客戶商品券**：某位客戶實際購買的一份方案，內容、售價與效期在購買時保存快照，後續修改方案不回寫已售出的商品券。
- **堂數異動**：預約保留、完課扣堂、取消釋放、人工調整、作廢等不可覆寫的流水紀錄。

### Core Business Rules

1. 組合方案內的每個項目都對應一筆現有課程及可使用堂數；方案名稱與售價可獨立於單次課程。
2. 商品券只可用於相同店家的客戶、課程與預約。
3. 預約開始時間必須落在商品券有效期內；超過效期的未來預約不可占用該券。
4. 有多張適用商品券時，依「最早到期」優先；同到期日再依「最早購買」優先。
5. 預約成功時立即保留一堂，避免同一餘額被多筆預約重複使用。
6. 預約改為 `completed` 時，保留轉為正式使用；改為 `cancelled` 時釋放保留。
7. `no_show` 預設視為使用一堂，但此規則列為發布前必須由產品負責人確認的政策。
8. 改期或改課程時必須重新檢查原商品券資格；不再符合時釋放舊保留並嘗試其他適用商品券。
9. `bookings.price` 繼續保存課程牌價快照；商品券支付來源及實際覆蓋堂數獨立記錄，避免破壞既有營收與客戶統計定義。
10. 方案下架或修改不影響已售商品券；刪除現有課程也不得抹除歷史商品券與使用紀錄。

### Functional Requirements

#### 商品券方案管理

- **FR-1**：管理員可建立商品券方案，必填名稱、售價、效期規則及至少一個兌換項目；售價不得小於 0，堂數必須為正整數。
- **FR-2**：每個兌換項目必須選擇一筆同店家的現有課程並設定堂數；同一方案中相同課程只能出現一次。
- **FR-3**：管理員可建立「單一課程多堂」及「多課程固定組合」兩種方案，系統顯示原價合計、售價、折扣金額與平均每堂價格供確認。
- **FR-4**：管理員可編輯尚未售出或未來銷售使用的方案設定；已售商品券維持購買時快照，不隨方案變更。
- **FR-5**：管理員可上／下架及軟刪除方案；下架後不可新增銷售，但既有客戶仍可依原規則兌換。

#### 銷售與客戶商品券

- **FR-6**：具銷售權限的員工可從既有客戶選擇一個上架方案，登記購買日期、實收金額、付款方式、效期與備註。
- **FR-7**：完成銷售後，系統建立唯一銷售編號及內容快照，立即顯示各課程的總堂數、已保留、已使用與可用堂數。
- **FR-8**：同一客戶可持有多份相同或不同方案；每份商品券必須個別追蹤效期與餘額。
- **FR-9**：尚未保留或使用任何堂數的誤登銷售可作廢；已有使用紀錄時不得直接刪除，須透過人工調整並保留稽核軌跡。

#### 預約套用與扣堂

- **FR-10**：建立預約時，後端依客戶、店家、課程、預約開始時間及可用餘額查找適用商品券；若有適用券，預設自動使用。
- **FR-11**：多張券均適用時，系統依最早到期、再依最早購買排序；後台員工可在送出前改選另一張適用券或選擇本次不使用，公開預約則採系統排序。
- **FR-12**：預約建立成功與堂數保留必須在同一個不可分割的後端交易完成；餘額不足或資格失效時整筆失敗，不得產生無對應的扣堂紀錄。
- **FR-13**：預約狀態改為 `completed` 時，將該筆保留轉為已使用；改為 `cancelled` 時釋放；重複更新同一狀態不得重複扣堂或歸還。
- **FR-14**：預約改期、改課程或改客戶時，系統重新驗證資格並以單一交易更新商品券保留；若找不到適用券，提示員工改為單次付費或取消變更。
- **FR-15**：預約開始時間超過商品券有效期時不可使用；已保留的預約不因今天跨過到期日而失效，只依該預約開始時間判斷。
- **FR-16**：系統不得讓任一兌換項目的「已保留＋已使用」超過總堂數，並須防止兩個裝置同時預約造成超扣。

#### 查詢、調整與通知

- **FR-17**：客戶詳情顯示其有效、已用完、已到期與已作廢商品券，以及每個課程的可用／保留／已使用堂數和效期。
- **FR-18**：預約詳情顯示本次是否使用商品券、方案名稱、扣抵課程及目前狀態；未使用時維持既有價格顯示。
- **FR-19**：管理員可人工增加、扣除或恢復堂數，但必須輸入原因；系統記錄操作者、時間、前後餘額及關聯預約。
- **FR-20**：商品券的銷售、作廢、保留、釋放、使用與人工調整均產生不可覆寫的稽核紀錄。
- **FR-21**：預約完成後的頁面及 LINE 通知可顯示「本次使用的商品券」與「該課程剩餘堂數」；無商品券時不顯示相關段落。
- **FR-22**：所有商品券資料必須套用店家隔離；一般成員不可建立方案、作廢銷售或人工調整，除非未來另行授權。
- **FR-23**：已透過 LINE／LIFF 安全連結客戶身分的使用者，可在客戶中心查看自己的近期預約、歷史預約及預約狀態；不得查詢其他客戶資料。
- **FR-24**：客戶中心可查看自己的有效、已用完與已到期商品券，以及各課程的可用、已保留、已使用堂數和效期；第一版僅供查看。

### User Experience

#### 管理端導覽

- 在「課程管理」旁新增「商品券」入口。
- 商品券頁含「方案」及「銷售紀錄」兩個頁籤。
- 客戶詳情 Drawer 新增「商品券」區塊，可直接登記購買及查看餘額。
- 新增／編輯預約的確認步驟顯示：
  - 有適用券：預設勾選「優先使用商品券」，顯示方案、效期及使用後剩餘堂數。
  - 無適用券：顯示原有單次課程價格，不增加阻擋。

#### 客戶預約

- 公開預約流程不要求客戶自行選券，避免選錯或暴露敏感購買資訊。
- 後端辨識既有客戶並完成預約後，才在成功頁回傳安全的使用摘要。
- LINE 通知以條件區塊顯示商品券名稱及該課程剩餘堂數。

#### LINE LIFF 客戶中心

- 在預約成功頁與 LINE 官方帳號選單提供「我的」入口。
- 頁面分為「我的預約」與「我的商品券」兩個頁籤，預設先顯示即將到來的預約。
- 身分已連結時直接使用 LINE／LIFF 驗證結果取得自己的資料，不要求另一組帳密。
- 身分未連結或驗證失敗時，不顯示任何預約或商品券資料，並引導使用者重新由 LINE 開啟或完成安全連結。
- 第一版不提供客戶自行取消、改期、購買、轉讓或調整堂數。

### Edge Cases

| Scenario | Expected Behavior |
|----------|------------------|
| 客戶有兩張都適用的券 | 自動選最早到期者；同日到期選最早購買者 |
| 最早到期券已無可用堂數 | 跳過並選下一張可用券 |
| 預約日期晚於券的到期日 | 不視為適用券，改走單次付費 |
| 券今天到期但預約在今天 | 依店家時區判斷，當日預約可使用 |
| 建立預約後取消 | 釋放原保留，餘額恢復且留下紀錄 |
| 已完課後又改回取消 | 不自動回補，要求管理員確認並以調整流程處理 |
| 預約改成另一個組合內課程 | 原保留釋放，再保留新課程對應堂數 |
| 預約改成不適用課程 | 提示改為單次付費或取消變更 |
| 兩個裝置同時使用最後一堂 | 僅一筆交易成功，另一筆收到餘額不足提示 |
| 方案價格或內容後續修改 | 已售商品券完全不變，新銷售使用新版設定 |
| 方案下架或刪除 | 停止新銷售；既有商品券仍可使用 |
| 對應課程被下架 | 不提供新預約時段；既有預約及歷史扣堂保留 |
| 商品券到期時仍有未使用堂數 | 狀態顯示已到期，不可再建立新保留；不自動刪除 |
| 商品券銷售誤登 | 零使用時允許作廢；已有使用時必須人工調整 |
| LINE 身分未連結 | 不影響商品券套用；僅略過 LINE 推播 |
| 未連結身分直接開啟「我的」 | 不回傳資料，顯示安全連結引導 |
| 同一 LINE 身分嘗試跨店查詢 | 僅回傳目前店家中已連結的客戶資料 |

## Technical Considerations

### Constraints

- 系統採 React、Supabase PostgreSQL、RLS 與 Edge Functions；商品券核心扣堂不可只在瀏覽器端執行。
- 所有金額沿用新台幣整數；若未來支援其他幣別，需另行擴充。
- 有效期計算與到期判斷必須使用店家 `timezone`，不可依瀏覽器本地時間。
- 既有 `bookings.price` 是課程牌價快照；商品券功能不得把它直接改成 0，也不得破壞既有 `client_stats` 統計。
- 新資料表、函數、RLS、索引及觸發器須由新增且可重複執行的 migration 建立，不修改已發布 migration。

### Integration Points

- `services`：商品券兌換項目只能引用同店家的現有課程。
- `clients`：每筆客戶商品券必須歸屬一位同店家客戶。
- `bookings`：保存商品券保留／使用關聯，但維持原課程價格快照。
- 預約建立與更新 RPC：負責資格檢查、排序、鎖定餘額及冪等狀態轉換。
- `notification_templates` 與 LINE Worker：加入商品券名稱、使用堂數及剩餘堂數等白名單變數。
- `audit_logs`：保存管理員調整、作廢與敏感狀態變更。

### Data Requirements

實作時至少需要能表達下列資料，但實際命名由技術設計決定：

- 商品券方案與方案兌換項目。
- 客戶購買紀錄與購買時的方案、價格、效期快照。
- 每個客戶商品券項目的總堂數與可計算餘額。
- 只新增不覆寫的堂數異動帳本，並可關聯預約及操作者。
- 預約與商品券保留／使用的唯一關聯，確保同一預約最多扣一次。

必要資料約束：

- 所有表包含 `store_id` 且受 RLS 保護。
- 堂數為正整數，金額不得為負數。
- 購買快照不可因方案更新而改變。
- 每個預約、商品券項目與扣堂動作具唯一或冪等約束。
- 查詢「客戶可用券」及「即將到期券」需有對應索引。

### Security & Audit

- 公開預約 API 只回傳本次是否套用及安全摘要，不可列出客戶所有商品券。
- 商品券資格、店家關係與餘額均由後端重新驗證，不信任前端傳入的商品券 ID 或金額。
- 使用資料庫鎖定或等效原子機制防止併發超扣。
- SECURITY DEFINER 函數固定 `search_path`，限制 EXECUTE 權限，並在函數內再次驗證店家及角色。
- 人工調整與作廢屬敏感操作，必須記錄操作者與原因。

### Observability

- 監測預約已完成但沒有對應扣堂、商品券負餘額、重複預約關聯及狀態不一致。
- 後端錯誤應使用可追蹤的錯誤代碼，例如 `VOUCHER_NOT_ELIGIBLE`、`VOUCHER_BALANCE_CHANGED`、`VOUCHER_EXPIRED`。
- 正式發布後前 14 天每日檢查異常計數，之後納入週期性營運檢查。

## Dependencies & Risks

### Dependencies

| Dependency | Owner | Status | Impact if Delayed |
|------------|-------|--------|-------------------|
| 商品券到期、未到場與退堂政策確認 | 產品負責人 | 待確認 | 無法凍結完整扣堂規則 |

### Risks

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| 併發預約造成最後一堂被重複使用 | Medium | High | 後端單一交易、列鎖／條件更新、唯一約束及併發測試 |
| 取消、改期或狀態回退造成重複扣放 | High | High | 狀態機、冪等鍵、只新增帳本及完整轉換測試 |
| 方案修改污染既有客戶權益 | Medium | High | 銷售時保存不可變快照，方案與持有券分層 |
| 到期日與時區產生爭議 | Medium | Medium | 以店家時區及預約開始時間為唯一判斷基準 |
| 商品券收入被重複計入既有預約營收 | Medium | High | 保留牌價快照，銷售收入與履約資料分離並明確報表定義 |
| 公開 API 洩露客戶商品券資訊 | Low | High | 僅回傳本次安全摘要、後端驗證身分、RLS 與跨店測試 |
| 已下架課程仍有剩餘堂數 | Medium | Medium | 保留權益與歷史，後台提示管理員換券或人工調整 |
| 首版同時納入金流導致範圍失控 | Medium | High | 線上付款明確列為非目標，先完成後台登記與扣堂閉環 |

## Open Questions

- [ ] **P0** `no_show` 是否固定扣一堂？建議：扣堂，但管理員可用「恢復堂數」調整。Owner：產品負責人
- [ ] **P0** 已完課後若改為取消，是否允許自動退堂？建議：不自動，改走人工恢復並填原因。Owner：產品負責人
- [ ] **P0** 商品券效期要支援「購買後 N 天／月」及「永不到期」即可，還是也要固定截止日？建議 MVP 支援購買後 N 天與永不到期。Owner：產品負責人
- [ ] **P0** 一般成員是否可登記銷售？建議：可以銷售，不可作廢或人工調整。Owner：產品負責人
- [ ] **P0** 商品券售價是否允許 0 元贈送券？建議：允許，但必須填寫備註。Owner：產品負責人
- [ ] **P1** 公開預約成功頁是否直接顯示剩餘堂數？建議：LINE／既有客戶身分已驗證時顯示，否則只顯示已套用。Owner：產品負責人
- [ ] **P1** 第一版付款方式選項為何？建議：現金、轉帳、信用卡、其他，僅供紀錄。Owner：產品負責人
- [ ] **P1** 「特別課程組合」是否只代表多種現有課程組合，或需要建立只在商品券內可見的新課程？建議第一版只組合現有課程；特殊內容仍先建立為現有課程再加入方案。Owner：產品負責人
