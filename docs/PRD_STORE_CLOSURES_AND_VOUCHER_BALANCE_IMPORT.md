## 1. Overview

本功能包含兩個彼此獨立、但都會影響預約可用性的管理能力：

1. **店家臨時店休**：管理員可針對國定假日、員工旅遊、維修或臨時事件，設定單日或連續多日店休。公開預約端不可選擇店休日，後台行事曆需清楚呈現店休與既有預約衝突。
2. **既有商品券餘額匯入**：系統正式上線前，店家可將客戶原本已購買、已使用一部分的商品券，以「期初餘額」方式同步進系統；後續若需修正，沿用現有的人工加減堂數與完整稽核紀錄。

### 1.1 現況與問題

- 店家目前只有固定營業時間與老師個人請假／封鎖時段，缺少「整間店暫停公開預約」的店級設定。
- 若只把所有老師逐一設為請假，操作繁瑣，也無法正確表達國定假日或員工旅遊等店級事件。
- 商品券目前已有管理員人工加減堂數功能，但缺少明確的「上線前資料移轉」入口。
- 若用「登記新購買，再人工扣除已使用堂數」模擬舊資料，容易讓銷售報表、原始堂數與已使用堂數的語意失真。

## 2. Goals and Success Metrics

### 2.1 Goals

- 管理員能在 1 分鐘內完成單日或連續多日店休設定。
- 公開預約流程無法顯示或建立落在店休日期內的預約。
- 新增店休時不會靜默取消既有預約，且管理員可立即看見衝突預約。
- 管理員可正確匯入客戶既有商品券的原始堂數、歷史已用堂數與目前可用堂數。
- 所有商品券期初匯入與後續人工調整皆可追查操作人、時間、原因與調整前後數值。

## 3. User Stories

### 3.1 店家臨時店休

- 身為管理員，我可以設定某一天為國定假日店休，讓客戶無法預約該日。
- 身為管理員，我可以設定員工旅遊的起訖日期，不必每天重複新增。
- 身為管理員，我可以填寫對外顯示名稱與內部備註，避免把內部資訊公開給客戶。
- 身為管理員，我希望新增店休時知道是否已有預約，避免誤以為系統已替我取消或通知客戶。
- 身為管理員，我可以修改或取消尚未結束的店休，讓可預約時段立即重新開放。
- 身為一般成員，我可以看到店休安排，但不能新增、修改或刪除。
- 身為客戶，我只能看到該日店休，不能看到員工旅遊原因或內部備註。

### 3.2 商品券期初餘額與人工調整

- 身為管理員，我可以選擇既有客戶與已建立的商品券方案，匯入上線前的商品券餘額。
- 身為管理員，我可以輸入原始總堂數與歷史已使用堂數，系統自動計算目前可用堂數。
- 身為管理員，我可以保留原購買日、到期日、歷史實收金額與移轉備註。
- 身為管理員，我希望期初匯入不被算成本月的新銷售收入。
- 身為管理員，我可以從客戶詳情或商品券銷售紀錄快速進入現有的人工加減堂數功能。
- 身為管理員，我無法把可用堂數扣成負數，或低於已被未來預約保留的堂數。
- 身為客戶，我在商品券頁面看到的是正確的目前可用堂數，不會看到內部移轉備註。

## 4. Scope

### 4.1 In Scope — 店家臨時店休

- 單日及連續多日的全天店休。
- 店休類型：國定假日、員工旅遊、維修、天候／緊急事件、其他。
- 對外顯示文字與內部備註分離。
- 設定、編輯、取消店休及稽核紀錄。
- 後台行事曆顯示店休標記。
- 儲存前偵測日期範圍內既有未取消預約，顯示數量與清單。
- 公開預約日期與時段查詢排除店休。
- 公開建立預約時於資料庫端再次驗證，避免直接呼叫 API 繞過。
- 店家時區下的日期範圍判斷，起訖日皆包含。

### 4.2 In Scope — 商品券

- 保留現有「人工增加／減少堂數」能力。
- 在客戶詳情與商品券銷售紀錄提供清楚的「調整堂數」入口。
- 新增「匯入既有商品券」流程，支援：
  - 客戶
  - 商品券方案
  - 原購買日
  - 到期日
  - 各課程原始總堂數
  - 各課程歷史已使用堂數
  - 歷史實收金額（選填）
  - 移轉原因／備註
- 以歷史使用紀錄呈現已使用堂數，不建立假的預約資料。
- 期初匯入標記與一般銷售分離，不灌入當期銷售收入。
- 匯入與調整後，預約抵扣立即使用正確餘額。

### 4.3 Out of Scope

- 自動同步台灣政府國定假日日曆。
- 每年自動重複的店休規則。
- 小時級的部分店休；部分時段仍使用營業時間或老師封鎖時段處理。
- 新增店休後自動取消、改期、退款或發送 LINE 通知。
- 大量 CSV 匯入；MVP 先提供逐位客戶的安全匯入。
- 自動比對舊系統預約與歷史商品券使用紀錄。
- 金流、發票或會計系統整合。

## 5. Solution Design

### 5.1 店休管理流程

1. 管理員進入「設定 → 臨時店休」。
2. 點擊「新增店休」，選擇起訖日期、類型、對外名稱與內部備註。
3. 系統即時查詢範圍內尚未取消的預約。
4. 若有衝突，顯示客戶、老師、課程與時間清單，明確說明「儲存店休不會取消既有預約」。
5. 管理員確認後儲存。
6. 公開預約端立即停用該日期，顯示「店休」或管理員設定的對外文字。
7. 後台行事曆顯示全天店休橫幅；既有預約仍保留並可個別處理。

### 5.2 後台店休期間新增預約政策（建議方案）

- **公開客戶**：不可覆寫，硬性阻擋。
- **一般成員**：不可覆寫，避免誤排。
- **管理員**：顯示醒目警告，二次確認後可覆寫店休建立特殊預約。

此政策延續目前「後台可為熟客安排營業時間外預約」的原則，同時讓店休比一般營業時間具有更高警示層級。

### 5.3 既有商品券匯入流程

1. 管理員進入「商品券 → 匯入既有商品券」，或從客戶詳情點擊相同入口。
2. 選擇客戶與已上架或封存但仍可匯入的商品券方案。
3. 依方案課程填入原始總堂數與歷史已使用堂數。
4. 系統顯示每門課的「目前可用 = 原始總堂數 − 歷史已使用堂數」。
5. 輸入原購買日、到期日、歷史實收金額與必填移轉備註。
6. 儲存後建立一筆標記為「期初匯入」的客戶商品券，以及不可竄改的歷史使用與稽核紀錄。
7. 後續修正一律透過既有人工加減堂數，不允許直接覆寫原始數值或刪除帳務軌跡。

### 5.4 商品券數量規則

- 原始總堂數必須大於 0。
- 歷史已使用堂數須介於 0 與原始總堂數之間。
- 初次匯入不接受保留堂數；舊系統尚未完成的預約應另行建立後，由現有預約機制自動保留。
- 人工減少後的有效總量不得小於「已使用 + 已保留」。
- 已失效或已作廢商品券預設不可調整；如需修正，先由管理員恢復有效狀態並留下原因。
- 同一次送出須在單一交易中完成，任一步驟失敗即全部回滾。

### 5.5 顯示與報表

- 商品券銷售紀錄標示來源：`一般銷售` 或 `期初匯入`。
- 期初匯入保留歷史實收資訊，但不計入系統上線後的當期新增銷售 KPI。
- 商品券詳情顯示：原始堂數、歷史匯入已用、系統內已用、已保留、人工調整、目前可用。
- 客戶端只顯示商品券名稱、適用課程、有效期限與目前可用堂數。

## 6. Technical Requirements

### 6.1 Database — 店休

新增 `store_closures`，最低欄位包含：

- `id`
- `store_id`
- `start_date`
- `end_date`
- `category`
- `public_label`
- `internal_note`
- `created_by`
- `created_at`
- `updated_at`
- `deleted_at`

要求：

- 日期範圍起日不得晚於迄日。
- 依 `store_id + 日期範圍` 建立查詢索引。
- 一般成員可讀同店資料；僅管理員可新增、修改與軟刪除。
- 對外 RPC 不得回傳 `internal_note` 或操作人資訊。
- `get_available_slots` 與公開建立預約 RPC 都必須檢查店休。
- 後台覆寫必須有明確的管理員權限檢查與稽核事件。

### 6.2 Database — 商品券

沿用既有：

- `client_vouchers`
- `client_voucher_items`
- `voucher_ledger`
- `adjust_client_voucher_item(...)`

新增或擴充：

- 商品券來源欄位，例如 `source = sale | opening_balance`。
- 期初匯入時間、匯入人與移轉備註。
- 可表達「歷史已使用」但不綁定假預約的帳本動作，例如 `opening_usage`。
- 專用原子 RPC，例如 `import_client_voucher_opening_balance(...)`。
- RPC 必須驗證同店客戶、同店方案、課程對應、管理員權限與數量範圍。
- 匯入不得直接接受前端提供 `store_id` 作為可信權限來源，店家範圍由登入者身分推導。
- 所有人工調整與匯入寫入既有稽核日誌。

### 6.3 Frontend

- 設定頁新增「臨時店休」管理區塊，手機版可完整操作。
- 新增店休表單使用既有 UI 元件庫，衝突預約以確認視窗呈現。
- 公開預約日曆將店休日設為不可選，顯示安全的對外文字。
- 後台行事曆以全天標記呈現店休，避免遮住預約卡片。
- 商品券頁新增「匯入既有商品券」。
- 客戶詳情與銷售紀錄增加「調整堂數」捷徑，沿用現有管理視窗。
- 所有數字輸入在送出時驗證，輸入過程不得強制覆寫使用者內容。

### 6.4 Security and Audit

- 店家隔離由 RLS 與 RPC 雙重保護。
- 僅管理員能建立店休、覆寫店休預約、匯入或人工調整商品券。
- 商品券不可由前端直接更新數量欄位，所有異動經由 RPC。
- 稽核內容至少包含操作人、時間、店家、原因、前值、後值與來源功能。
- 不在前端紀錄或顯示 service role、LINE Secret 或其他敏感資訊。

## 7. Acceptance Criteria

### 7.1 店休

- [ ] 管理員可建立單日及跨日店休。
- [ ] 非管理員無法新增、修改或取消店休。
- [ ] 公開預約端看不到店休日期的可預約時段。
- [ ] 即使直接呼叫公開預約 RPC，也無法建立店休期間預約。
- [ ] 新增店休與既有預約衝突時，必須先顯示清單並確認。
- [ ] 儲存店休不會自動取消或修改既有預約。
- [ ] 管理員覆寫建立預約時有二次確認及稽核紀錄。
- [ ] 取消店休後，符合其他規則的時段重新開放。
- [ ] 客戶看不到內部備註。

### 7.2 商品券

- [ ] 可匯入原始 10 堂、歷史已用 4 堂，完成後顯示可用 6 堂。
- [ ] 匯入資料不建立假的預約。
- [ ] 匯入資料不計入本月新增銷售 KPI。
- [ ] 預約對應課程時可正常保留並扣抵匯入後餘額。
- [ ] 管理員可從客戶詳情及銷售紀錄進入人工調整。
- [ ] 人工減少不可低於已使用加已保留堂數。
- [ ] 非管理員無法匯入或調整。
- [ ] 重複送出或任一步驟失敗時，不會產生半套資料。
- [ ] 每筆匯入與調整可查到操作人、原因與前後數值。

## 8. Dependencies and Risks

| 項目 | 風險 | 緩解方式 |
| --- | --- | --- |
| 店休與既有預約 | 使用者誤以為店休會自動取消預約 | 儲存前列出衝突，明示不會自動取消 |
| 公開預約快取 | 設定後短時間仍顯示舊時段 | 店休異動後重新查詢；建立時由 DB 再驗證 |
| 管理員覆寫 | 特殊預約被誤用 | 僅管理員、二次確認、完整稽核 |
| 商品券歷史資料 | 把期初資料算成新銷售 | 加入明確來源欄位，KPI 排除 opening balance |
| 商品券並行異動 | 同時預約與人工調整造成超扣 | RPC 交易、資料列鎖定與 DB 約束 |
| 舊方案對應 | 舊商品券找不到現有方案 | 匯入前先建立／封存對應方案，不接受自由文字方案 |

## 9. Milestones

1. **M1 — 資料層**
   - 店休資料表、RLS、索引、稽核。
   - 可用時段與公開建立預約的店休防線。
   - 商品券期初匯入欄位、帳本動作與原子 RPC。
2. **M2 — 店休後台與公開端**
   - 設定頁店休管理、衝突預約提示。
   - 行事曆標示、公開預約不可選。
3. **M3 — 商品券匯入與入口優化**
   - 期初匯入表單。
   - 客戶詳情與銷售紀錄的調整捷徑。
   - 報表排除期初匯入。
4. **M4 — 驗證與發布**
   - RLS、並行、跨店與帳務一致性測試。
   - 手機與桌面流程驗證。
   - QC 通過後發布 staging，由使用者驗收再決定 production。

## 10. Open Questions

以下採建議預設值實作，若產品決策不同需在開工前調整：

1. **店休期間後台預約**：建議僅管理員可在二次確認後覆寫；一般成員不可覆寫。
2. **對外店休原因**：建議預設只顯示「店休」，管理員可另外填安全的對外文字。
3. **歷史實收金額**：建議允許選填並保留作歷史資訊，但不納入上線後銷售 KPI。
4. **匯入方式**：MVP 建議逐位客戶匯入；CSV 大量移轉另開後續需求。

## 11. Agent Execution Contract

### 11.1 Authoritative Sources

- 本 PRD。
- `docs/PRD_VOUCHER_PACKAGES.md` 的既有商品券帳務規則。
- 目前已部署的 Supabase migration、RPC 與 RLS 定義。
- 專案 `AGENTS.md` 的開發、保護、QC 與發布規則。

### 11.2 Required Delivery Order

1. 先載入 Supabase Postgres best practices，完成資料庫與安全設計。
2. 資料庫 migration 與測試通過後提交獨立檢查點。
3. 再載入 frontend-design，分批完成店休與商品券前端。
4. 修改受保護頁面前先說明範圍並取得確認。
5. 每個 User Story 修改 1–3 個相關檔案後立即提交。
6. 功能完成後執行 QC；QC 失敗不得提交或部署。
7. 先發布 staging，取得使用者明確確認後才能進 production。

### 11.3 Do Not Touch

- 不修改既有已執行 migration；只新增向前 migration。
- 不重寫、刪除或回填既有商品券帳本資料。
- 不自動取消、刪除或改期既有預約。
- 不將 staging 或 production 密鑰寫入程式碼或 Git。
- 不把期初匯入偽裝成新銷售或建立假預約。

### 11.4 Stop Conditions

遇到下列情況須停止並請使用者決策：

- 需要自動取消、退款或通知店休期間既有預約。
- 需要把舊商品券歷史使用逐筆對應到舊預約。
- 需要支援大量 CSV 匯入或跨店搬移。
- 需改變既有商品券扣抵優先順序或帳務定義。
- 資料庫現況與本 PRD 的數量語意不一致，可能影響既有資料。
