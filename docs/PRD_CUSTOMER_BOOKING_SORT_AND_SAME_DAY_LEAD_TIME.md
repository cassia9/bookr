# PRD：C 端課程分類排序與當日最早可預約時間

## Overview

### Problem Statement

目前 C 端預約頁的課程清單由公開目錄依課程名稱排序，當課程數量增加時，客戶難以快速辨識課程類型，也無法依療程時間或價格找到合適選項。

此外，客戶端可選時段目前固定限制為「現在起 2 小時後」，店家無法依當日人力、備料時間或現場狀況調整。即使店家臨時可以接單，也只能等待固定時間；忙碌時也無法把準備時間拉長。

### Solution Summary

本次交付包含兩項彼此相關的 C 端預約體驗改善：

1. 建立店家自訂的課程類別，C 端依類別分組，並提供時間與價格的升冪／降冪排序。
2. 在後台設定頁提供 15、30、60、120 分鐘四種「當日最早可預約時間」，儲存後立即套用於客戶端可用時段與最後送出驗證。

### Target Users

- 預約客戶：希望快速找到適合預算與時間的課程。
- 店家管理員：希望依當天營運狀況即時調整客戶最早可預約時間。
- 店家一般成員：可查看目前設定，但不可修改全店預約規則。

## Goals & Success Metrics

### Goals

1. 讓客戶能以課程類別、療程時間與價格快速找到合適服務。
2. 讓管理員不需部署或聯絡工程人員，即可調整當日即時預約緩衝時間。
3. 確保前端顯示與最後建立預約採用相同規則，避免過早預約被建立。
4. 保留現有店家的預約行為；功能上線後，未主動調整的店家仍維持 2 小時限制。

### Success Metrics

| Metric | Current Baseline | Target | Timeline |
|--------|------------------|--------|----------|
| 課程排序規則正確率 | 僅依名稱排序 | 自動化案例 100% 通過 | Staging 驗收前 |
| 早於店家設定門檻且成功建立的 C 端預約 | 尚未在最終送出層強制阻擋 | 0 筆 | 上線後持續監控 |
| 設定儲存成功率 | 無此設定 | 排除網路中斷後 ≥ 99.9% | 上線後 30 天 |
| C 端排序操作回應時間 | 無此操作 | p95 < 100ms | Staging 效能驗證 |
| 預約流程完成率 | 上線前 30 天基準 | 不低於基準 5% 以上 | 上線後 30 天 |

### Non-Goals

- 不提供客戶自行建立或編輯課程類別。
- 不讓店家輸入任意分鐘數；MVP 僅提供 15、30、60、120 分鐘。
- 不改變後台人工新增預約可忽略營業時間的既有規則。
- 不支援針對單一課程、單一老師或單一日期設定不同緩衝時間。
- 不在本次建立推薦演算法、個人化排序或動態定價。

## Scope

### In Scope

- 店家層級的課程類別資料與類別顯示順序。
- 課程可指定一個類別；舊課程與未分類課程歸入「其他服務」。
- C 端課程頁的類別篩選與排序選單。
- 排序選項：推薦排序、時間短到長、時間長到短、價格低到高、價格高到低。
- 後台課程管理可指定課程類別，並提供基本的類別新增、改名、排序與停用能力。
- 後台設定頁新增「當日最早可預約時間」。
- 同日可用時段查詢與公開預約送出時的雙重驗證。
- 網頁預約與 LINE LIFF 預約共用相同規則。
- 店家時區、營業時間、店休、老師封鎖、既有預約與服務時長的既有檢查仍然有效。
- 設定異動寫入稽核紀錄。

### Out of Scope

- 多層分類、標籤系統或一門課同時屬於多個類別。
- 依熱門度、評分、老師或商品券資格排序。
- 類別圖片、行銷橫幅或 SEO 頁面。
- 預約前一天、數天或數週的最早／最晚預約限制。
- 對既有預約進行自動取消或改期。
- 後台人工新增預約套用 C 端即時預約限制。

### Future Considerations

- 每週或特定日期覆寫最早可預約時間，適合假日與活動日。
- 針對不同課程設定準備時間。
- 儲存客戶上次選擇的排序方式。
- 熱門、最近預約過、商品券可用等個人化排序。

## Solution Design

### Functional Requirements

#### 課程類別與管理

- FR-1：每個店家可建立自己的課程類別；類別至少包含名稱、顯示順序、啟用狀態與店家識別。
- FR-2：每門課程最多歸屬一個類別；既有或未指定類別的課程在 C 端統一顯示於「其他服務」，且排在最後。
- FR-3：管理員可在課程管理中新增、改名、排序與停用類別，並可替課程指定類別。
- FR-4：停用或刪除類別不得刪除課程；受影響課程回到「其他服務」。
- FR-5：一般成員可讀取同店類別與課程對應，但不得修改類別或課程分類。

#### C 端篩選與排序

- FR-6：C 端服務步驟顯示「全部」及已啟用類別篩選；類別依店家設定順序排列，「其他服務」固定在最後。
- FR-7：C 端提供五種排序：推薦排序、時間短到長、時間長到短、價格低到高、價格高到低。
- FR-8：「全部」模式維持類別分組，排序只在各類別內生效；選擇單一類別時，只顯示該類別課程並套用相同排序。
- FR-9：推薦排序固定為「類別順序 → 時間短到長 → 價格低到高 → 課程名稱 → 課程 ID」，確保每次結果一致。
- FR-10：時間或價格相同時，以課程名稱、課程 ID 作穩定排序；價格為 0 的免費課程視為最低價格。
- FR-11：切換篩選或排序不得清除已載入的店家、LINE 身分或其他預約草稿資料；選取課程後維持既有五步驟預約流程。
- FR-12：停用、軟刪除或不屬於該店家的課程與類別不得出現在公開目錄。

#### 當日最早可預約時間設定

- FR-13：設定頁提供 15、30、60、120 分鐘四個選項，顯示文字分別為「15 分鐘後」「30 分鐘後」「1 小時後」「2 小時後」。
- FR-14：既有店家與新店家的預設值均為 120 分鐘，以維持目前固定 2 小時的行為。
- FR-15：僅管理員可修改設定；一般成員可查看目前值但不可變更。
- FR-16：設定儲存成功後立即生效，不需重新部署、清除快取或重新登入。
- FR-17：可選時段以店家時區的目前時間加上設定分鐘數作為門檻，再向上取整至既有 15 分鐘時段格；開始時間大於或等於門檻才可由時段查詢回傳並顯示，早於門檻的時段不得讓客戶看見或選擇。
- FR-18：此門檻只影響「今天」；未來日期仍依營業時間、店休、老師封鎖、既有預約、緩衝時間與服務時長判斷。
- FR-19：網頁預約與 LINE LIFF 預約在最後建立預約時必須再次讀取最新設定並驗證，不可只依賴畫面曾顯示過的時段。
- FR-20：若客戶停留頁面期間設定改變，且原時段已不符合新門檻，送出時不得建立預約，並提示「店家已更新最早可預約時間，請重新選擇時段」。
- FR-21：後台由管理員或成員人工新增的預約不套用此門檻，保留特殊熟客時段與營業時間外預約能力。
- FR-22：設定異動須記錄店家、操作人、修改時間、修改前值與修改後值。

### User Experience

#### C 端服務選擇

1. 標題與說明下方顯示橫向可捲動的類別籤：「全部、基礎修復、進階修復、其他服務」。
2. 類別籤下方提供「排序」選單，預設為「推薦排序」。
3. 「全部」模式以類別標題分區，讓客戶知道服務的語意歸屬；排序不跨類別混排。
4. 手機版維持單欄課程卡，篩選籤可水平滑動；排序使用既有 `Select` 元件，避免自製下拉選單。
5. 當篩選後沒有課程時，顯示「此類別目前沒有可預約服務」，並提供返回「全部」的操作。

#### 後台設定

1. 在「設定 → 渠道設定 → 預約設定」加入「當日最早可預約時間」。
2. 使用既有 `Select` 元件顯示四種選項。
3. 輔助文字說明：「例如現在 10:07，選擇 30 分鐘後，最早顯示 10:45 的可用時段。」
4. 與確認模式、開放線上預約一起由「儲存此區設定」提交。
5. 儲存成功顯示成功提示；失敗時保留畫面輸入值並顯示可理解的錯誤。

#### C 端門檻檢查流程

1. 客戶進入「時段」步驟時，後端以最新店家設定產生可用時段，早於門檻的時段不回傳，因此客戶平常不會先選到再於送出時才被告知失敗。
2. 若現在為 10:00、店家設定 60 分鐘，最早可顯示 11:00；10:15、10:30、10:45 均不得出現。
3. 若現在為 10:07、店家設定 60 分鐘，門檻為 11:07，向上對齊後最早顯示 11:15。
4. 最後送出驗證只作為安全防線，用來處理客戶頁面開啟過久、裝置休眠或店家在客戶選取後提高門檻等過期狀態。
5. 過期時段送出失敗後，畫面提示店家已更新最早可預約時間，清除舊時段並引導客戶返回時段步驟重新選擇。

#### 後台課程分類

1. 在課程新增／編輯表單加入「課程類別」選擇欄位。
2. 在課程管理頁提供精簡的「管理類別」入口，不新增獨立主選單頁。
3. 類別排序支援明確的上移／下移操作；MVP 不要求拖曳排序。

### Edge Cases

| Scenario | Expected Behavior |
|----------|------------------|
| 舊課程沒有類別 | 顯示於「其他服務」，不阻擋預約 |
| 類別被停用但仍有課程 | 課程移至「其他服務」，不刪除課程 |
| 類別同名 | 同一店家內阻擋重複名稱；不同店家可同名 |
| 多個課程時間與價格相同 | 依名稱與 ID 穩定排序，重新整理後順序不跳動 |
| 免費課程依價格升冪 | 免費課程排在最前；降冪則排在最後 |
| 現在 10:07，設定 30 分鐘 | 門檻為 10:37，最早 15 分鐘格為 10:45 |
| 現在 10:15，設定 15 分鐘 | 10:30 可顯示，因開始時間等於門檻 |
| 設定門檻已超過今日最後可完成時段 | 今日顯示無可預約時段，未來日期不受影響 |
| 客戶開頁後管理員從 15 分鐘改成 2 小時 | 原時段送出失敗，提示重新選擇；不可靜默改到其他時段 |
| 客戶裝置時間錯誤 | 以資料庫／伺服器時間與店家時區判斷，不信任裝置時間 |
| 夏令時間或非台灣時區店家 | 使用 `stores.timezone` 計算；無值才以 `Asia/Taipei` 安全兜底 |
| 網頁與 LINE LIFF 同時送出同一時段 | 沿用既有衝突檢查，只能成功一筆 |
| 管理員後台安排 5 分鐘後的熟客預約 | 不受 C 端最早預約門檻限制，維持既有能力 |

## Technical Considerations

### Constraints

- 現有 `services` 尚無類別欄位，公開目錄目前只回傳名稱、描述、分鐘數與價格。
- 現有 `get_available_slots` 以固定 `NOW() + INTERVAL '2 hours'` 過濾，並使用 15 分鐘時段格。
- 現有公開預約有網頁 RPC 與 LINE Edge Function 兩條建立路徑，兩者必須共用相同資料庫端驗證。
- `BookingPage.tsx` 屬於業務關鍵敏感檔案，實作前須先讀取、提出變更計畫並取得確認。
- 所有資料庫變更須遵循冪等 migration、同店 RLS、最小權限與安全的 `search_path`。

### Integration Points

- 公開預約目錄：擴充 `get_public_booking_catalog`，只回傳啟用類別與公開必要欄位。
- 可用時段：擴充 `get_available_slots`，由店家設定取代固定 2 小時。
- 公開網頁預約：`create_booking_public` 在建立前執行相同門檻驗證。
- LINE LIFF 預約：`create_line_booking`／`line-booking` 路徑使用同一資料庫規則，不在 Edge Function 複製時間算法。
- 後台設定：沿用現有 `stores` 設定與「儲存此區設定」流程。
- 稽核：沿用 `audit_logs`，記錄設定前後值。

### Data Requirements

建議資料模型：

- `service_categories`
  - `id`
  - `store_id`
  - `name`
  - `sort_order`
  - `active`
  - `created_at`
  - `updated_at`
  - `deleted_at`
- `services.category_id`：可為空，外鍵指向 `service_categories.id`。
- `stores.same_day_booking_lead_minutes`：整數，允許值為 15、30、60、120，預設 120。

資料與安全要求：

- 類別名稱在同店、未刪除範圍內唯一。
- 類別讀寫皆以 `store_id` 隔離；公開端只能透過白名單 RPC 取得必要欄位。
- 公開 RPC 不回傳停用類別、內部稽核欄位或其他店家資料。
- migration 上線後既有店家自動取得 120 分鐘，不改變現行客戶端行為。
- 類別與設定修改應寫入稽核紀錄。
- 建議將最早預約門檻驗證抽成資料庫函式供時段查詢與兩條建立路徑共用，避免規則漂移。

### Stop and Escalate

| Condition | Escalate to |
|-----------|-------------|
| 產品希望「全部」模式跨類別做全域價格／時間混排，與本 PRD 的分組規則不同 | 產品負責人／使用者 |
| 希望既有店家上線後預設不是 120 分鐘 | 產品負責人／使用者 |
| 找不到可讓網頁與 LINE 共用的資料庫端最終驗證點 | 技術負責人 |
| 需放寬既有 RLS、公開更多店家或課程欄位才能實作 | 技術負責人 + 安全審查 |
| 發現 `stores.timezone` 缺失、無效或正式資料含未知時區 | 技術負責人 + 店家管理者 |
| migration 會刪除、改寫既有課程、預約或商品券資料 | 立即停止並回報使用者 |
| 需要修改超過 5 個檔案且尚未建立提交檢查點 | 立即停止，先拆分並提交既有階段 |

## Dependencies & Risks

### Dependencies

| Dependency | Owner | Status | Impact if Delayed |
|------------|-------|--------|-------------------|
| 課程類別資料模型與 RLS | 後端／資料庫 | 待實作 | C 端無法可靠依類別分組 |
| 公開目錄 RPC 擴充 | 後端／資料庫 | 待實作 | C 端拿不到類別與排序資訊 |
| 設定頁與課程管理 UI | 前端 | 待實作 | 管理員無法維護類別或門檻 |
| 公開預約最終驗證共用規則 | 後端／資料庫 | 待實作 | 可能發生畫面與送出規則不一致 |
| QC、Staging 測試資料與 LINE 測試帳號 | QA／產品 | 可用 | 無法驗證完整雙路徑流程 |

### Risks

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| 舊課程沒有分類造成清單混亂 | H | M | migration 不強制回填，統一放入「其他服務」並提供後台補分類 |
| 時段查詢與最後送出使用不同規則 | M | H | 將門檻判斷集中於資料庫函式，兩條建立路徑強制共用 |
| 使用客戶裝置時間造成時區或改時鐘繞過 | M | H | 僅使用資料庫／伺服器時間與店家時區 |
| 管理員改設定後，已開頁客戶送出失敗 | M | M | 最終拒絕並提供明確重新選擇提示，不靜默變更時段 |
| 新分類 UI 增加手機版高度與操作負擔 | M | M | 橫向籤列、單一排序選單、前端設計與手機 E2E 驗證 |
| 跨店類別資料外洩 | L | H | 複合唯一性、RLS、公開白名單 RPC 與跨店測試 |
| 預設值改變既有店家預約行為 | L | H | migration 預設 120 分鐘，等同現行固定值 |
