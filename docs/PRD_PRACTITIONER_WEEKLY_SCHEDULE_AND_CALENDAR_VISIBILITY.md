# PRD：老師個別上班日、休假與預約管理資訊呈現

## Overview

### Problem Statement

目前公開預約時段主要依照店家營業時間產生，再排除店休、老師封鎖時段與既有預約；系統尚未保存並套用每位老師的固定上班日。因此只在週三、週四上班的老師，仍可能在其他星期被客戶選到。

後台雖已有老師休假與店休資料，但預約管理的呈現仍不完整：店休已有日期標記，老師休假未在目前實際使用的行事曆完整顯示；預約卡片主要以顏色區分老師，老師姓名只在部分詳細資訊或滑鼠提示中出現，手機上尤其不直觀。

此外，專案同時保留 `practitioner_leaves` 與 `practitioner_blocks` 兩套老師休假資料來源；目前休假管理畫面寫入 `practitioner_blocks`，部分統計卻讀取 `practitioner_leaves`，可能造成「已設定休假但統計或行事曆看不到」的不一致。

### Solution Summary

本功能將提供：

1. 每位老師獨立的每週固定上班日與單一工作時段設定。
2. 公開預約端依「店家營業時間 ∩ 老師上班時段」產生可預約時段，再排除店休、老師休假與既有預約。
3. 預約管理的月、週、日與甘特圖清楚顯示店休、老師休假與非排班狀態。
4. 所有預約卡片直接顯示老師姓名，不再只靠顏色辨識。
5. 統一以 `practitioner_blocks` 作為老師例外休假來源，保留舊資料並安全遷移，不直接刪除舊表。

### Target Users

- 店家管理員：設定老師固定班表、老師休假與特殊預約。
- 一般成員／老師：查看班表、休假、店休與自己的預約安排。
- 預約客戶：只看到實際有老師能服務的日期與時段。

## Goals & Success Metrics

### Goals

1. 避免客戶預約到老師固定不上班的日期或時段。
2. 讓管理者在預約管理中立即辨識老師、休假與店休。
3. 保留後台特殊安排彈性，同時留下明確警告與稽核紀錄。
4. 消除兩套老師休假資料來源造成的顯示不一致。

### Success Metrics

| Metric | Current Baseline | Target | Timeline |
|--------|-----------------|--------|----------|
| C 端出現老師非上班時段 | 尚未檢查固定班表 | 0 筆 | 上線後持續監控 |
| 直接呼叫公開預約流程繞過班表／休假／店休 | 班表尚無最終驗證 | 0 筆 | 上線後持續監控 |

### Non-Goals

- 本期不製作自動排班、輪班演算法或工時薪資計算。
- 本期不支援同一天多段班（例如 09:00–12:00、14:00–18:00）。
- 本期不自動取消、改期或通知已存在的衝突預約。
- 本期不製作拖曳式整月班表或大量匯入班表。

## Scope

### In Scope

- 老師管理新增「排班與休假」入口。
- 每位老師設定週一至週日是否上班。
- 每個上班日設定一段開始與結束時間，預設帶入店家營業時間。
- 未設定新班表的既有老師，維持目前「依店家營業時間每天可預約」的舊行為。
- 客戶端日期與時段查詢套用老師固定班表。
- 公開建立預約時由資料庫再次驗證班表、休假與店休。
- 老師休假維持單日／連續多日全天設定。
- 儲存班表或休假前顯示受影響的既有預約，不自動取消。
- 預約管理月、週、日與甘特圖顯示店休、老師休假／非排班。
- 所有預約卡片顯示老師姓名；狹窄手機畫面允許縮寫但可點開看完整名稱。
- 修正「今日休假」等統計，統一讀取實際使用的休假來源。
- 店家隔離、管理員權限與稽核紀錄。

### Out of Scope

- 一天兩段以上班別與午休切段。
- 隔週班、每月第幾週、單次加班日等複雜規則。
- 排班複製到其他老師、CSV 匯入或批次編輯。
- 自動通知受班表變更影響的客戶。
- 老師自行登入修改自己的班表或提出請假申請。
- 工時統計、加班、薪資與出勤打卡。

### Future Considerations

- 多時段班與固定休息時間：待確認實際使用需求後擴充資料模型。
- 單次加班／臨時可上班日：可作為班表例外資料，不改固定週班表。
- 班表範本與批次套用：老師數量增加後再評估。
- 老師個人入口與請假審核：需要角色、通知與審核流程，另案規劃。

## Solution Design

### Functional Requirements

#### A. 老師每週固定班表

- FR-1：管理員可在老師管理開啟「排班與休假」，查看該老師週一至週日設定。
- FR-2：每個星期日可獨立設定「上班／不上班」；上班日需有一段開始與結束時間。
- FR-3：第一次設定班表時，上班時間預設為店家營業時間；管理員至少需保留一個上班日，若需完全停止接單應使用老師「停用」。
- FR-4：同一老師同一星期日只能有一筆有效規則；結束時間必須晚於開始時間。
- FR-5：既有老師若尚無班表設定，系統必須沿用目前每天依店家營業時間開放的行為，避免發布後突然關閉預約。
- FR-6：新增老師時可先使用預設班表；未手動儲存前仍採相同的向下相容規則。

#### B. 可預約時段與最終防線

- FR-7：C 端可預約時段須為「店家營業時間、老師固定上班時段」的交集，再排除店休、老師休假、停用老師、未指派課程與預約衝突。
- FR-8：客戶選擇「不指定老師」時，只要至少一位可執行該課程的老師符合所有條件，該時段才可顯示。
- FR-9：客戶指定老師時，該老師非上班日或休假期間不得顯示時段。
- FR-10：最終建立公開預約的資料庫流程必須重新檢查班表、休假、店休及衝突；前端顯示過的舊時段不得繞過最新設定。
- FR-11：班表或休假在客戶預約流程中途被修改時，送出應回傳可理解的錯誤並引導重新選時段。

#### C. 老師休假與既有資料整合

- FR-12：老師休假以 `practitioner_blocks` 為唯一新寫入來源，支援單日或連續多日全天休假及選填原因。
- FR-13：不得直接刪除 `practitioner_leaves`；發布前需檢查舊資料並以可重複執行的方式回填到 `practitioner_blocks`，完成核對後停止新寫入舊表。
- FR-14：重疊休假不得靜默建立；系統應提示並避免產生重複封鎖資料。
- FR-15：一般成員可讀同店班表與休假，只有管理員可新增、修改或移除。

#### D. 班表／休假變更與既有預約

- FR-16：儲存班表或新增休假前，系統須列出未取消、且將落在新不可用區間內的既有預約數量與明細。
- FR-17：確認儲存後不得自動取消、改期或通知既有預約；這些預約需在預約管理標示為「班表衝突」或「休假衝突」。
- FR-18：管理員可保留衝突預約並逐筆處理；系統不得因後續查詢而隱藏既有預約。
- FR-19：每次班表與休假新增、修改、移除皆需記錄操作人、老師、前後值、時間與原因。

#### E. 預約管理資訊呈現

- FR-20：月視圖需顯示店休標記；老師休假以簡潔摘要顯示，例如「休假：王、林」，超過可用空間顯示「+N 位」。
- FR-21：週／日視圖需在對應日期或時段顯示店休與老師休假標記，不可遮住既有預約卡片。
- FR-22：甘特圖需在老師列上顯示休假或非排班遮罩，並標示「休假」或「非排班」。
- FR-23：所有預約卡片至少顯示客戶與老師；空間足夠時再顯示課程與時間。不得只用老師顏色表達身分。
- FR-24：休假原因屬店內資訊，只能在登入後台顯示；C 端不得取得或顯示休假原因。
- FR-25：店休與老師休假同日發生時，店休為第一層狀態，老師休假可收合於詳細資訊，不重複占滿畫面。

#### F. 後台特殊預約政策

- FR-26：C 端不可覆寫班表、老師休假或店休。
- FR-27：建議僅管理員可在後台覆寫非排班日或老師休假建立特殊預約；送出前需顯示原因與二次確認。
- FR-28：覆寫成功後需留下稽核事件，包含被覆寫的規則、操作者與預約 ID。
- FR-29：後台仍維持 24 小時時間選擇，不因店家營業時間或老師固定班表縮短畫面；不可用區間以視覺提示表達。

### User Experience

#### 老師管理

建議把現有「休假」操作升級為「排班與休假」，使用置中的 Modal 或 Drawer，分成兩個頁籤：

1. **固定上班日**：七列星期設定；每列包含開關、開始時間、結束時間。
2. **臨時休假**：沿用現有日期範圍與原因，並顯示未來休假清單。

老師列表直接顯示摘要，例如：

`週三、週四 · 09:00–18:00`
若每天時間不同，顯示 `週三 09:00–18:00、週四 12:00–20:00`；超過兩組以「查看完整班表」收合。

#### 預約管理

- 月視圖：日期格上方依序顯示店休、老師休假摘要，再顯示預約卡片。
- 週／日視圖：日期標頭顯示店休與當日休假老師；時間格的預約卡直接顯示老師。
- 甘特圖：老師本身即為列標題，休假／非排班時段用淡紅／灰色斜線遮罩。
- 手機版預約卡建議格式：第一行客戶，第二行 `老師 · 課程`；若空間不足，保留老師、課程可省略。

### Recommended Admin Override Policy

沿用現有「後台可替熟客建立營業時間外預約」原則：

- 公開客戶：硬性阻擋。
- 一般成員：預設不可覆寫。
- 管理員：可二次確認後覆寫，並留下稽核紀錄。

這項政策需在實作前由產品負責人最終確認；若不允許覆寫，FR-27、FR-28 改為全面阻擋。

### Edge Cases

| Scenario | Expected Behavior |
|----------|------------------|
| 既有老師沒有新班表資料 | 維持目前每天依店家營業時間可預約，不改變正式站行為 |
| 老師只設定週三、週四 | 其他星期不出現該老師的公開時段 |
| 所有老師當日均不上班或休假 | 日期可標示無可預約時段；不得進入可送出的時間選擇 |
| 店家營業 09:00–21:00，老師班表 12:00–18:00 | C 端僅顯示 12:00–18:00 內可容納完整課程的時段 |
| 老師班表超出店家營業時間 | C 端只取交集；後台仍可經規則覆寫建立特殊預約 |
| 課程跨越老師下班時間 | 該開始時段不可顯示，也不可由公開送出流程建立 |
| 新增休假時已有預約 | 顯示衝突清單；確認後保留預約並標示衝突 |
| 同日同時為店休與老師休假 | 行事曆優先顯示店休，老師休假置於詳細資訊 |
| 客戶停留頁面期間班表被修改 | 最終送出失敗並提示重新選擇，不建立半套資料 |
| 老師停用 | 不再出現在 C 端選擇與可用時段，但歷史預約仍保留姓名快照／關聯顯示 |

## Technical Considerations

### Constraints

- 店家時區仍以 `stores.timezone` 為準；星期判斷不可使用瀏覽器本地時區或固定 `+08:00` 字串。
- 公開查詢只能回傳安全資訊，不得暴露休假原因、內部備註或其他老師私人資料。
- 現有 `CalendarPage.tsx` 為業務關鍵敏感檔案，實作前須先讀取、說明改動並依規範提交檢查點。
- 不得直接刪除 `practitioner_leaves` 或既有休假資料。
- 公開可用時段與建立預約的驗證必須共用相同規則，避免查詢可見但送出失敗的長期漂移。

### Proposed Data Model

新增 `practitioner_weekly_schedules`，建議欄位：

- `id`
- `store_id`
- `practitioner_id`
- `weekday`：ISO 1–7（週一至週日）
- `is_working`
- `start_time`：不上班時可為 `NULL`
- `end_time`：不上班時可為 `NULL`
- `created_at`
- `updated_at`
- `updated_by`

必要規則：

- 唯一鍵：`practitioner_id + weekday`。
- 第一次儲存時於同一交易寫入完整七天，之後不可用「缺少資料」代表不上班。
- 無任何班表列代表尚未設定，沿用舊行為；已有班表時必須完整七天。
- 上班日必須同時具有開始與結束時間，且 `end_time > start_time`。
- `store_id` 必須與老師所屬店家一致，不接受前端自行指定為權限依據。
- 依 `store_id, practitioner_id, weekday` 建立查詢索引。

### Existing Leave Data

- 新功能以 `practitioner_blocks` 作為例外不可預約時段的權威來源。
- 發布 migration 僅做安全回填與去重，不刪除 `practitioner_leaves`。
- 完成資料核對前保留舊表唯讀；後續清理另開技術債，不與本次功能一起破壞性移除。

### Integration Points

- `get_public_available_slots(...)`：加入每週班表與完整課程時長檢查。
- 公開建立預約 RPC：加入相同的最終班表／休假／店休驗證。
- 後台建立與調整預約 RPC：加入覆寫政策、角色驗證與稽核。
- 老師管理：讀寫班表、休假與衝突預約。
- `BookingManagement`、`CalendarPage`、`GanttPage`：讀取可見區間的店休、班表與老師封鎖。
- 老師統計：將「今日休假」改為讀取 `practitioner_blocks`。

### Performance & Security

- 公開可用時段查詢應先依星期排除不上班老師，再產生／交叉比對時段，避免無效候選爆量。
- 班表、休假與店休查詢須以店家及日期／星期索引支援。
- RLS：一般成員只能讀同店資料；管理員才能寫入同店班表與休假。
- 所有 `SECURITY DEFINER` 函數固定 `search_path = ''`，完整限定 schema，並只授權必要角色。
- 任何覆寫都不可只信任前端布林值，必須在資料庫重新檢查管理員權限。

當規格與舊程式註解衝突時，以本 PRD 與最新 timestamp migration 為準；若資料庫實際 schema 與 migration 不一致，停止並由產品負責人與資料庫負責人確認。

### Do Not Touch

| Path or system | Reason it is off limits |
|----------------|-------------------------|
| 正式資料庫中的既有預約與休假資料 | 不可為了補班表而刪除或重建真實營運資料 |
| `practitioner_leaves` 表的破壞性刪除 | 尚需先比對是否存在舊資料與完成安全回填 |
| 商品券、LINE 圖文選單、邀請註冊流程 | 與本功能無關，避免引入跨模組回歸 |
| 後台 24 小時特殊預約能力 | 既有明確需求，班表只能提示／依核准政策覆寫，不得縮回店家營業時間 |

### Requirement Verification Map

| Requirement | How it is verified | Who verifies |
|-------------|--------------------|--------------|
| FR-1–FR-6 | 建立只有週三、週四上班的老師，重新進入頁面後資料一致；舊老師未設定時行為不變 | Automated + QA |
| FR-7–FR-11 | 以指定／不指定老師測試上班日、非上班日、休假、店休、流程中改班表與直接 RPC 送出 | DB tests + QA |
| FR-12–FR-15 | 建立、重疊、刪除休假；驗證舊資料回填、跨店與一般成員寫入均被拒絕 | DB tests + QA |
| FR-16–FR-19 | 調整會影響既有預約的班表／休假，確認衝突清單、預約保留與稽核事件 | Integration + QA |
| FR-20–FR-25 | 月、週、日、甘特圖及手機寬度逐一檢查店休、休假、老師姓名與資訊優先序 | Visual QA + PM |

### Stop and Escalate

| Condition | Escalate to |
|-----------|-------------|
| 正式資料同時大量存在 `practitioner_leaves` 與 `practitioner_blocks`，且無法安全去重 | 產品負責人 + 資料庫負責人 |
| 需要決定一般成員是否能覆寫老師休假／非排班 | 產品負責人 |
| 需求改為一天多段班、隔週班或單次加班 | 產品負責人，重新評估資料模型與範圍 |
| 現有公開預約 RPC 與最新 migration 不一致 | 資料庫負責人，先確認正式環境狀態 |
| 實作需要刪除既有資料或修改商品券／邀請／LINE 主流程 | 產品負責人，停止擴張範圍 |

## Dependencies & Risks

### Dependencies

| Dependency | Owner | Status | Impact if Delayed |
|------------|-------|--------|-------------------|
| 管理員覆寫政策最終確認 | 產品負責人 | 待確認 | 影響後台送出規則與稽核驗收 |
| 正式休假舊資料盤點 | 資料庫負責人 | 待執行 | 無法安全統一資料來源 |
| 現有公開時段與預約 RPC 測試基線 | 工程／QA | 已有部分測試 | 規則調整容易造成 C 端回歸 |
| 行事曆手機版視覺驗收 | 產品負責人／QA | 待設計 | 標記過多可能降低可讀性 |

### Risks

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| 新班表使既有老師突然不可預約 | M | H | 無班表資料維持舊行為；第一階段不強制回填 |
| 查詢規則與最終送出規則不同步 | M | H | 共用判斷函數／測試矩陣，送出端再次驗證 |
| 班表變更與既有預約衝突 | H | H | 儲存前列出衝突；保留預約並標記，不自動取消 |
| 兩套休假資料造成漏擋或重複顯示 | H | H | 以 blocks 為新權威來源，先回填去重、舊表不刪除 |
| 月曆同日標記過多造成手機破版 | M | M | 店休優先、休假摘要 +N、詳細資訊延後展開 |
| 可用時段查詢變慢 | M | M | 先依星期排除老師、補索引、對可視日期範圍查詢 |
| 管理員誤用覆寫 | M | M | 二次確認、醒目警告、管理員限定、audit log |

### QA Scenarios

1. 未設定班表的既有老師。
