# PRD：行事曆快速新增與固定循環預約

## Overview

### Problem Statement

Bookr 已能從後台建立單筆預約，也已在行事曆接收部分空白時段點擊事件，但目前月、週、日視角的觸發範圍與日期時間預填行為尚未形成一致且可驗收的規則。操作人員仍可能需要重新選擇剛剛點擊的日期或時間，也可能誤點標題、既有預約或非時段區域後意外開啟表單。

另一方面，固定每週同一時段回訪的客戶仍需逐筆建立預約。這不只耗時，也容易漏建、重複建立或在取消時誤以為只處理單次。循環預約還會影響時段衝突、商品券保留、LINE 推播、後台通知與稽核紀錄，不能只在前端複製多筆資料。

### Solution Summary

本期提供兩項互補能力：

1. 在後台 24 小時制行事曆的月／週／日視角點擊有效空白區域時，直接開啟現有新增預約視窗，並正確預填點擊的日期與時間；管理端可安排營業時間外的特殊預約，點擊非時段區域則不執行任何新增動作。
2. 在新增預約時可選擇「固定每週重複」，設定間隔與結束條件。後端先一次檢查全部時段，再以單一交易建立具相同系列識別的具體預約。取消系列中的預約時，可選擇只取消本次，或取消本系列尚未發生的有效預約。

此功能為確定性排程與交易邏輯，不包含 AI 產生內容。

### Target Users

- 店家管理員：替固定回訪客戶快速建立與管理一系列預約。
- 店家一般成員：依角色權限建立及取消自己店家的預約。
- 從業人員：查看排程時可辨識循環預約，並避免重複安排時段。
- 客戶：收到清楚、不重複洗版的預約與取消通知。

## Goals & Success Metrics

### Goals

1. 讓操作人員從行事曆點擊到開啟已預填表單的時間低於 1 秒。
2. 讓固定每週預約可在一次操作中完成，並維持現有衝突與商品券規則。
3. 讓單次取消與系列取消的範圍清楚、可追溯且可安全重試。
4. 不破壞單筆預約、拖曳改期、完課、商品券與 LINE 通知流程。
5. 清楚區隔後台特殊預約能力與公開預約限制，避免一般客人取得營業時間外時段。

### Non-Goals

- 不支援客戶在公開預約頁自行建立循環預約。
- 不支援每日、每月、任意星期組合或複雜 RRULE 規則。
- 不支援「修改本次及未來所有預約」；第一版編輯只影響選定的一次。
- 不支援跨店、跨客戶、跨課程或每次不同從業人員的系列。
- 不支援永久無上限循環；必須提供可計算的結束條件。

## Scope

### In Scope

- 後台行事曆月、週、日視角的有效空白區域點擊新增。
- 後台完整 24 小時時間軸、`HH:mm` 顯示、點擊日期／時間預填及 15 分鐘時段對齊。
- 管理端可在營業時間外建立單筆或循環特殊預約；公開預約仍受店家營業時間限制。
- 新增預約視窗中的固定每週重複設定。
- 每 1 至 4 週重複一次，使用「重複次數」或「結束日期」停止。
- 建立前顯示總次數、第一筆、最後一筆及衝突摘要。
- 循環系列資料、具體預約關聯、RLS、索引與稽核資料。
- 全系列的原子衝突檢查與原子建立。
- 取消單次或取消同系列尚未發生的 `pending`／`confirmed` 預約。
- 與現有商品券保留／釋放、LINE 通知及後台通知中心整合。
- 行事曆及預約詳情顯示循環標記與系列摘要。

### Out of Scope

- 甘特圖空白格的本次點擊規格調整；保留現況。
- 客戶端建立或管理循環預約。
- 客戶端查看、選擇或建立店家營業時間外的特殊時段。
- 系列層級批次改期、改課程、改客戶或改從業人員。
- 取消已完課、未到場、已取消或已開始的歷史預約。
- 跨時區系列與夏令時間轉換；本期以店家時區建立固定當地時間。
- 自動候補、空位推薦與衝突自動改排。

### Future Considerations

- 編輯本次／本次及未來／整個系列。
- 每日、每月、指定多個星期與例外日期。
- 客戶端自助取消單次或後續系列。
- 系列暫停、恢復與批次更換從業人員。
- 甘特圖點擊體驗與行事曆統一。

## Solution Design

### Product Rules

1. 月視角的日期空白格視為有效新增區域；預填該格日期及「目前時間的下一個 15 分鐘時段」。若已晚於 `23:45`，維持所選日期並預填 `23:45`，不得偷偷換到隔日。
2. 後台週、日視角採 `00:00–24:00` 的完整時間軸與 `HH:mm` 顯示；只允許時間網格觸發，並預填點擊位置代表的日期與 15 分鐘時段。
3. 店家營業時間只限制公開預約可取得的時段，不限制具權限的後台操作人員。營業時間外在後台以淡色背景及「營業外」提示區分，但仍可點擊、建立、編輯及建立循環預約。
4. 點擊既有預約、緩衝區、封鎖時段、日期標題、星期標題、全天列、工具列、滾動條或視圖外空白均不開啟新增表單。
5. 第一版循環規則為固定每週：相同店家、客戶、從業人員、課程、星期、開始時間、緩衝時間、備註與商品券策略。
6. 系列最多 52 次且最遠不超過 12 個月；至少建立 2 次，避免把單筆預約誤標成系列。
7. 系統在送出前檢查所有發生日期；任一筆與預約、緩衝或封鎖時段衝突時，不建立任何一筆，並列出衝突日期供修正。
8. 每一筆系列預約都是真實 `bookings` 記錄，因此可獨立確認、完課、未到場、改期或取消；系列識別只用於關聯與批次操作。
9. 「取消整個系列」實際範圍為同系列中尚未開始且狀態為 `pending`／`confirmed` 的預約；歷史與終態資料保留不變。
10. 系列操作必須冪等；網路重試不可建立重複系列、重複預約、重複扣券或重複取消。
11. 後台忽略營業時間不等於忽略安全限制；從業人員封鎖、既有預約與緩衝衝突仍須阻止建立。

### Functional Requirements

#### 行事曆快速新增

- **FR-1**：月視角點擊日期空白格時，開啟現有新增預約視窗，日期為所點日期，時間為目前時間向上對齊下一個 15 分鐘時段；結果不得跨日，當日上限為 `23:45`。
- **FR-2**：週視角點擊有效空白時段時，依橫向日期欄及縱向時間位置預填日期與 15 分鐘時段。
- **FR-3**：日視角點擊有效空白時段時，預填目前檢視日期及點擊位置代表的 15 分鐘時段。
- **FR-4**：點擊既有預約、緩衝區、封鎖時段、表頭、全天列、工具列或非時間格區域時，不開啟新增預約視窗，也不覆寫目前表單狀態。
- **FR-5**：每次開啟新增預約視窗都以最新點擊來源重設日期與時間；手動修改後關閉再點另一格，不得沿用舊值。
- **FR-6**：後台週／日行事曆及時間選擇器須使用完整 24 小時制與 `HH:mm` 格式，允許 `00:00–23:45` 的 15 分鐘起始時段。營業時間外可建立預約，但須有淡色「營業外」視覺提示；不得因超出營業時間而拒絕管理端送出。

#### 固定循環預約建立

- **FR-7**：新增模式提供「重複預約」開關；關閉時維持現有單筆建立流程，編輯模式不顯示此開關。
- **FR-8**：開啟後可設定每 1、2、3 或 4 週重複，並二選一設定重複總次數或結束日期；系統限制 2–52 次且最後日期不超過 12 個月。
- **FR-9**：表單即時顯示重複星期、開始時間、預計總次數、第一筆及最後一筆日期，日期範圍變更時重新計算。
- **FR-10**：送出時由後端重新計算發生日期並檢查每筆從業人員封鎖、預約與緩衝衝突；不得信任前端傳入的展開清單。
- **FR-11**：系列、所有具體預約及其必要關聯必須在同一資料庫交易中建立；任一筆失敗時全部回滾，並回傳可辨識的錯誤代碼與衝突日期。
- **FR-12**：系列建立成功後，行事曆立即重新整理，成功訊息顯示建立筆數及日期範圍；每筆預約可個別開啟詳情。

#### 商品券、通知與價格

- **FR-13**：循環建立沿用現有商品券策略並逐筆依該次預約日期檢查資格；自動模式依現行到期排序保留，可用堂數不足的其餘預約維持單次付費，不得超扣或產生負餘額。
- **FR-14**：若操作人員指定特定商品券，該券必須能覆蓋系列中所有符合效期的預約；餘額不足時阻止整批建立，提示改用自動選券、減少次數或改為單次付費。
- **FR-15**：每筆預約保留自己的課程價格快照及商品券關聯；取消本次或系列時，沿用既有規則逐筆釋放尚未使用的商品券保留。
- **FR-16**：建立系列時對客戶只發送一則整合摘要，包含次數、固定星期／時間及首末日期；不得為每個未來預約各發一則 LINE 訊息。
- **FR-17**：後台通知中心不得因管理員一次建立系列而產生大量重複待辦；若建立者與收件人不同，使用一則系列摘要，並仍可連到系列第一筆或系列檢視。

#### 系列辨識與取消

- **FR-18**：系列預約在行事曆卡片與詳情顯示「循環」標記、目前為第幾次及系列總次數；單筆預約不顯示。
- **FR-19**：取消系列中的未來有效預約時，確認視窗提供「只取消這次」及「取消本系列尚未發生的預約」；按鈕文字須包含預計影響筆數。
- **FR-20**：「只取消這次」只更新所選預約；系列其餘預約與規則不變，該次保留在系列歷史中並標示已取消。
- **FR-21**：「取消本系列尚未發生的預約」只處理開始時間晚於操作當下且狀態為 `pending`／`confirmed` 的預約；已開始、已完課、未到場及已取消者不變。
- **FR-22**：取消系列必須在單一交易中更新預約、釋放商品券保留並寫入稽核紀錄；重複送出不得重複釋放。
- **FR-23**：編輯某次循環預約只影響該次，並在詳情顯示「此變更不會套用至其他循環預約」；系列未來預約維持原設定。

#### 安全與稽核

- **FR-24**：循環系列與預約均套用店家隔離及既有角色權限；跨店家系列 ID 不得被讀取、建立、取消或推測。
- **FR-25**：建立系列、取消單次及取消系列都記錄操作者、時間、影響筆數、系列 ID 與作用範圍；不得刪除歷史預約。

### User Experience

#### 行事曆點擊

- 月視角：點日期格空白處即開啟新增視窗；日期數字、既有預約及「更多」入口仍維持原用途。
- 週／日視角：顯示 `00:00–24:00` 完整時間軸並以 `HH:mm` 標示；首次進入時自動捲動到目前時間附近，避免每天都從午夜開始操作。
- 營業時間外：以淡色背景或邊界呈現並標示「營業外」，游標及點擊行為仍與營業時間內相同，讓管理者可替熟客安排特殊時段。
- 可新增空白時段：游標移入時顯示輕微 hover 回饋；點擊後視窗中的日期與時間需立即可見。
- 所有視角：事件卡片優先處理自身點擊，不可冒泡成新增預約。

#### 重複設定

新增預約表單在日期時間區下方顯示：

```text
[ ] 重複預約

開啟後：
每 [1] 週重複
結束方式  (●) 共 [8] 次  ( ) 至 [日期]

預計建立 8 次
每週三 14:00｜09/16 至 11/04
```

送出按鈕依狀態顯示「建立 8 筆預約」。建立前若發現衝突，Modal 保留輸入並顯示最多前 5 個衝突日期，其餘以筆數摘要呈現。

#### 取消確認

```text
這是循環預約的第 3／8 次

[只取消 9/30 這次]
[取消本系列後續 6 次]
[返回]
```

系列取消屬高影響操作，需二次確認並再次顯示影響筆數；完成後顯示實際取消數與略過數。

### Edge Cases

| Scenario | Expected Behavior |
|----------|------------------|
| 月視角點擊上／下個月的灰色日期 | 仍以畫面顯示的實際日期開啟，不以目前月份推算 |
| 月視角點擊日期格中的既有預約 | 只開啟預約詳情，不開新增視窗 |
| 點擊封鎖或緩衝區 | 維持現有查看／無動作行為，不開新增視窗 |
| 月視角操作時間在營業時間外 | 仍預填目前時間對齊的 15 分鐘時段，允許管理端建立 |
| 月視角操作時間晚於 23:45 | 維持所點日期並預填 `23:45`，不跨到隔天 |
| 點擊 00:00–開店前或關店後–23:45 的空白格 | 顯示營業外提示，但正常開啟表單並允許送出 |
| 一般客人查詢營業時間外時段 | 公開時段 API 不回傳，公開預約頁不可選擇或自行輸入 |
| 營業時間外與既有預約／封鎖衝突 | 仍阻止建立；管理端只能忽略營業時間，不能忽略衝突或封鎖 |
| 系列跨月或跨年 | 依店家時區保留固定星期與當地時間 |
| 結束日期無對應發生日 | 建立到結束日期之前最後一個合法發生日 |
| 系列中一筆與既有預約衝突 | 整批不建立，回傳衝突日期與既有預約摘要 |
| 系列中一筆落在從業人員封鎖時段 | 整批不建立，提示封鎖日期 |
| 商品券只能覆蓋部分次數 | 自動模式先保留可用堂數，其餘為單次付費；摘要分開顯示 |
| 指定券餘額不足 | 整批阻止，要求改變商品券策略或次數 |
| 重複點擊送出或網路重試 | 使用冪等鍵回傳同一結果，不新增第二個系列 |
| 取消系列時部分預約已完課 | 已完課不變，只取消尚未開始的有效預約 |
| 系列中的單次已手動改期 | 仍屬原系列；取消系列時依新的開始時間判斷是否為未來預約 |
| 兩位操作人員同時取消系列 | 最終狀態一致，商品券只釋放一次 |
| 系列建立者就是通知收件人 | 不產生自我待辦洗版；保留稽核紀錄 |

## Technical Considerations

### Constraints

- 既有前端使用 React、`react-big-calendar`、Supabase PostgreSQL 與 RLS。
- `BookingsPage.tsx` 與 `supabase/migrations/*` 為受保護檔案，實作前需依 `AGENTS.md` 再確認修改計畫。
- 不修改任何已發布 migration；新增一份冪等 migration 與對應 pgTAP 測試。
- 批次建立、衝突檢查、商品券保留及系列取消必須由資料庫交易完成，不可由瀏覽器逐筆呼叫。
- 所有日期展開以店家時區為準，資料庫仍保存 `TIMESTAMPTZ`。
- 管理端建立 RPC 不得套用店家營業時間限制；公開預約時段 RPC 與公開建立流程必須繼續驗證店家營業時間，兩者不可共用會放寬公開權限的參數。

### Integration Points

- `src/pages/admin/BookingsPage.tsx`：月／週／日空白格事件與取消確認入口。
- `src/components/booking/NewBookingModal.tsx`：日期時間預填及重複設定；既有單筆流程必須保留。
- 公開預約時段查詢與建立 RPC：只做回歸驗證，不變更營業時間限制或暴露管理端繞過能力。
- `upsert_booking_with_voucher`：單筆建立與商品券規則的權威來源；批次 RPC 應重用等價驗證，避免邏輯分叉。
- `bookings`：新增可選系列關聯，不改變既有單筆資料語意。
- LINE 通知佇列及後台通知中心：系列建立／取消應聚合，避免每筆訊息洗版。
- `audit_logs`：保存系列建立與取消範圍。

### Data Requirements

實作至少需要能表達：

- 循環系列 ID、店家、建立者、固定每週間隔、原始時區、起始日期、結束條件與建立時摘要。
- 每筆 booking 對應的系列 ID 與系列序號；單筆預約欄位可為空。
- 建立請求的冪等鍵，防止重試產生重複系列。
- 系列層級稽核事件及實際影響筆數。

必要約束與索引：

- 系列與 booking 的 `store_id` 必須一致。
- `(series_id, occurrence_index)` 唯一。
- 同一店家下的建立冪等鍵唯一。
- 索引支援依 `series_id`、`store_id`、未來開始時間與有效狀態查詢。
- RLS 及 SECURITY DEFINER RPC 必須固定 `search_path`、收回不必要的 public EXECUTE，並在函數內驗證角色與店家。

### Observability

- 記錄批次建立的要求筆數、成功筆數、衝突筆數與執行時間，不記錄客戶敏感內容。
- 監測同系列序號重複、部分批次寫入、商品券負餘額及系列取消後仍保留堂數。
- 使用可辨識錯誤碼，例如 `RECURRENCE_INVALID`、`RECURRENCE_LIMIT_EXCEEDED`、`SERIES_TIME_CONFLICT`、`SERIES_PRACTITIONER_BLOCKED`、`SERIES_VOUCHER_INSUFFICIENT`。
